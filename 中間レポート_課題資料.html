AIの使い方

GitHub Copilot や ChatGPT などの AI は使ってかまいません。ただし、この中間レポートでは、AIは「相談相手」で、「答えを出す人」ではありません。

してよいこと

  • コマンドやエラーの意味を聞く
  • od の出力を見せて、「どう読めばよいか」を聞く
  • 自分の書いたコードの間違いを探してもらう
  • 自分の説明の文章が分かりにくくないか見てもらう

しないこと

  • 「この課題を全部やって」と頼む
  • AIが作った数字（測っていない時間など）をそのまま書く
  • 説明できない行を、そのままレポートに貼る
AIを使ったら、レポートの「AIとのやり取り」欄に必ず書いてください。書くのは3つ：①何を聞いたか（聞いた文そのまま）　②何が返ってきたか（要点でよい）　③それを自分でどう確かめたか（打ったコマンドと結果）。
AIを使わなかった人は「使わなかった」と1行書けばOKです。減点も加点もしません。
この課題で AI が「間違えやすい」ところ　AIは、あなたのコンピュータで測った時間も、あなた専用のファイルの中身も知りません。一般論としてはもっともらしい答えを返しますが、あなたの結果と合うとは限りません。合わなかったときに「どちらが正しいか」を確かめるのが、この課題の中心です。

課題1：1回に読む量を変えると、何が起きるか

ファイルをコピーするプログラム bufcp は、「何バイトずつ読んで書くか」を自分で決められます。この大きさを 1バイトから1MBまで変えて、かかる時間を測ります。

使うファイル　bufcp.c　measure.sh　stdcp.c 記録　kadai1.log 目安　2〜3時間

しくみの復習：read と write は「カーネルへのお願い」

read も write もシステムコールです。1回呼ぶたびに、プログラムは「カーネル（OSの中心部分）にお願いして、仕事をしてもらう」という手続きをします。この手続きには、毎回いくらかの時間がかかります。

バッファが小さいと、お願いの回数がとても多くなります。大きいと回数は少なくなります。では、大きければ大きいほど速いのでしょうか？ それを測るのがこの課題です。

必須問1-1　まず予測する（動かす前に）

✎ 予測ファイルを作る VSCode で ~/syspro/midterm/predict1.txt を作り、次の3つに自分の予測を書いて保存してください。AIに聞く前に書くこと。
  1. 10MB（10,485,760バイト）のファイルを 1バイトずつコピーすると、read は何回呼ばれるか。
  2. そのコピーに、だいたい何秒かかるか。
  3. 1, 4, 16, …, 1MB のうち、いちばん速いのはどの大きさか。理由も1行で。

必須問1-2　bufcp に「回数を数える」機能を足す

bufcp.c には TODO と書かれたところが2か所あります。read を呼んだ回数と write を呼んだ回数を数えて、最後に表示するように書き足してください。

  1. VSCode で bufcp.c を開き、TODO を探す（Ctrl+F で検索できます）。
  2. 回数を数える変数を2つ用意し、ループの中で増やす。
  3. 最後に、標準エラー出力に表示する。fprintf(stderr, ...) を使います（第3週目の「標準出力と標準エラー出力」を思い出してください）。
  4. コンパイルして動かす。
gcc -Wall -o bufcp bufcp.c          # コンパイル（-Wall：注意すべき点を全部教えてもらう）
head -c 10M /dev/urandom > big.dat  # でたらめなバイトを10MB分作って big.dat に保存
./bufcp big.dat copy.dat 4096       # 4096バイトずつコピーしてみる
cmp big.dat copy.dat                # 2つのファイルが同じか比べる（何も出なければ同じ）
こんな表示になればOK（read の回数は、数え方によって 2560 になる人もいます）
read: 2561 回, write: 2560 回
head -c 10M /dev/urandomテスト用のファイルを作る

何をするhead -c 数 は「先頭から、そのバイト数だけ取り出す」。/dev/urandom は読むたびにでたらめなバイトが出てくる特別なファイルです。10M は 10×1024×1024 = 10,485,760 バイト。

注意> を忘れると、でたらめなバイトが画面に10MB分流れます。止まらなくなったら Ctrl+C。

cmp ファイル1 ファイル2比べる

何をする2つのファイルを1バイトずつ比べます。同じなら何も表示しません（Unix では「何も言わない＝うまくいった」が普通です）。違うと、最初に違ったバイトの位置を教えてくれます。

ヒント：どこに何を書けばよいか（詰まったら開く）
変数は long nr = 0, nw = 0; のように、ループの前に用意します。read が成功したらループの中で nr++;、write が成功したら nw++;。表示は fprintf(stderr, "read: %ld 回, write: %ld 回\n", nr, nw);。
考えてほしいこと：ループの条件 (n = read(...)) > 0 が「偽」になったときの read は、何回目に数えるべきでしょうか？　表示が read: 2560 回 になった人と 2561 回 になった人がいるはずです。どちらが本当の呼び出し回数かを、問1-2の答えで説明してください。

問1-2 で書くこと

  • 書き足した行をすべて貼り、1行ずつ何をしているか説明する。
  • 4096バイトのとき read が 2561回になる理由を、計算式で示す（10,485,760 ÷ 4096 = ？　では、残りの1回は何？）。
  • 余裕があれば表示を標準出力ではなく標準エラー出力にした理由を書く（ヒント：./bufcp big.dat copy.dat 4096 > /dev/null としても回数は見えるか？）。

必須問1-3　大きさを変えて、時間を測る

配布セットの measure.sh は、バッファの大きさを 1, 4, 16, 64, 256, 1024, 4096, 16384, 65536, 262144, 1048576 と4倍ずつ変えながら、それぞれ3回ずつ bufcp を動かして時間を測るシェルスクリプトです。

#!/bin/bash
# measure.sh : バッファの大きさを変えながら bufcp の時間を測る
for size in 1 4 16 64 256 1024 4096 16384 65536 262144 1048576
do
    for i in 1 2 3
    do
        echo "=== size=$size  ${i}回目 ==="
        time ./bufcp big.dat copy.dat $size
    done
done
for 変数 in 値の並び; do … doneくり返し

何をする『Linux標準教科書』のシェルスクリプトの章に出てくる「くり返し」です。in の後ろに並べた値を1つずつ size に入れて、do と done の間を実行します。$size と書くと、その時の値に置き換わります。

time コマンド時間を測る

何をする後ろのコマンドを実行し、終わったら3つの時間を表示します。

real時計で測った時間（実際に待った時間）

userあなたのプログラム自身が計算していた時間

sysカーネルが、あなたのお願い（システムコール）を処理していた時間

では、記録を取りながら実行します。1バイトのときは1回に数秒かかるので、全部で1分ほど待ちます。

cd ~/syspro/midterm
script kadai1.log        # ここから記録を始める
cat predict1.txt         # 最初に、自分の予測を記録に残す
uname -a                 # どんなコンピュータで測ったかを残す
nproc                    # CPUの数
./bufcp big.dat copy.dat 4096
./measure.sh             # 測る（1分ほどかかる）
exit                     # 記録を終える（kadai1.log ができる）
こんな表示がたくさん出ます（数字は人によって違います）
=== size=1  1回目 ===
read: 10485761 回, write: 10485760 回

real	0m5.505s
user	0m0.959s
sys	0m4.473s

問1-3 で書くこと

  • 結果を表にする。列は「バッファの大きさ・read の回数・real・user・sys」。3回のうち真ん中の値を使う（3回の値がどれくらいばらついたかも1行で書く）。
  • グラフにする（Google スプレッドシートや Excel でよい）。横軸はバッファの大きさ、縦軸は時間。横軸は「対数目盛」にすること（1, 4, 16, … が等間隔に並ぶ目盛り。スプレッドシートのグラフ設定で選べます）。
ヒント：たくさんの結果から、数字だけを取り出したい
パイプでつなげば、ログから必要な行だけ取り出せます（第3週目のパイプ）。
grep real kadai1.log　← real の行だけを表示
grep -E '^(=== size|real|user|sys)' kadai1.log　← 見出しと3つの時間の行だけを表示
手で写してもかまいません。

必須問1-4　結果を説明する

問1-4 で書くこと（それぞれ3〜6行）

  • (a)　バッファが小さいとき、real のほとんどは user と sys のどちらが占めていたか。それは何を意味するか。上の図の言葉（「お願いの手続き」）を使って説明する。
  • (b)　バッファを4倍にすると、時間はだいたい何分の1になったか。read の回数の変わり方と比べて、何が言えるか。
  • (c)　どこから先は、大きくしても速くならなくなったか。その大きさを、次のコマンドで分かる数字と比べる。 
    getconf PAGESIZE     # メモリを管理する「ページ」1枚の大きさ
stat -f -c %S .      # 今いる場所のファイルシステムの「ブロック」1つの大きさ
  • (d)　予測（問1-1）と結果が違ったところを1つ以上挙げ、なぜ違ったと思うかを書く。全部当たった人は、いちばん意外だった数字について書く。
見てほしいところ　大きなバッファのところでは、3回の結果がばらついたり、大きくしたのに遅くなったりすることがあります。それは「失敗」ではなく観察結果です。「なぜだろう」と考えて書いてください（正解は1つではありません）。

余裕があれば問1-5　1文字ずつなのに、なぜ速い？

stdcp.c は 1文字ずつコピーするプログラムです。ただし read/write ではなく、標準入出力ライブラリの getc/putc を使っています。

gcc -Wall -o stdcp stdcp.c
time ./stdcp big.dat copy2.dat                # 1文字ずつコピー（getc/putc）
time ./bufcp big.dat copy.dat 1               # 1バイトずつコピー（read/write）
strace -c -e trace=read,write ./stdcp big.dat copy2.dat   # システムコールの回数を数える
strace -cのぞき見

何をするプログラムが呼んだシステムコールを数えて、最後に表にしてくれます。-e trace=read,write で「read と write だけ数えて」と指定しています。

注意strace がない環境もあります（command not found）。その場合は時間の比較だけでかまいません。また、./bufcp big.dat copy.dat 1 を strace で動かすと、何分も終わりません（1000万回以上を1回ずつ記録するため）。試すなら head -c 100K big.dat > small.dat で小さいファイルを作ってから。

問1-5 で書くこと

  • stdcp と bufcp 1 の時間を比べ、なぜこんなに違うのかを説明する。strace が使えた人は、read が何回呼ばれたかと、そこから分かるライブラリの中のバッファの大きさを書く。

課題2：中身の分からないファイルを読み解く

あなた専用のファイル mystery_○○○○○○○○○○.dat を渡します。中身の形は教えません。od コマンドでバイトを1つずつ見て、どんな形のデータが並んでいるかを突き止め、それを読むCのプログラムを書きます。

使うファイル　practice.dat　practice_reader.c　reader.c　自分の mystery_….dat 記録　kadai2.log 目安　2〜3時間

ファイルについて分かっていること（全員共通）

仕様メモある気温の記録ファイル（ここに書いてあることだけが手がかり）
  • ファイルは、同じ形・同じ大きさの「記録（レコード）」が何件か、すき間なく並んだものです。
  • 1件の記録には、4つの項目が入っています：番号（整数）・場所の名前（英小文字の文字列）・記録した時刻（1970年1月1日からの秒数）・気温（小数）。
  • 4つの項目の順番と、それぞれ何バイトかは、人によって違います。
  • このファイルは、Cの構造体の配列を write でそのまま書き出したものです（いつもの x86-64 の Linux で）。
  • 番号は1件ごとに1ずつ増えますが、1か所だけ番号が抜けています。
第5週目の od を思い出してください。practice.dat では、kyoto と nara のあいだに「ここで1件が終わり」という印はありませんでした。ファイルには区切りの印がありません。区切りを決めているのは、読む側です。

必須問2-1　練習：見本のファイルを読んでみる

いきなり自分のファイルは難しいので、まず形が分かっている practice.dat で、od の読み方を練習します。practice.dat の1件は次の形です。

struct record {
    int32_t number;     /* 番号（4バイトの整数） */
    char    name[8];    /* 場所の名前（8バイト。後ろは \0 で埋まっている） */
    double  value;      /* 気温（8バイトの小数） */
};
cd ~/syspro/midterm
ls -l practice.dat              # ファイルの大きさを見る（72バイトのはず）
od -A d -t x1 practice.dat      # 1バイトずつ、16進数で表示する
こう表示されます
0000000 01 00 00 00 6b 79 6f 74 6f 00 00 00 00 00 00 00
0000016 00 00 00 00 00 00 29 40 02 00 00 00 6e 61 72 61
0000032 00 00 00 00 00 00 00 00 00 00 00 00 00 80 23 40
0000048 03 00 00 00 6f 73 61 6b 61 00 00 00 00 00 00 00
0000064 00 00 00 00 00 00 2e 40
0000072
odバイトをのぞく

何をするファイルの中身を、1バイトずつ数字で表示します（octal dump の略）。cat では文字として読めないファイルも、od なら何が入っているか見えます。

-A d左端の数字（何バイト目か）を10進数で表示する。0000016 は「この行は16バイト目から」という意味。

-t x11バイトずつ（1）、16進数（x）で表示する。

よく使う表示のしかた od -A d -c ファイル … 文字として読めるものは文字で（名前を探すとき） od -A d -t d4 ファイル … 4バイトずつ整数として（int32_t） od -A d -t d2 ファイル … 2バイトずつ整数として（int16_t） od -A d -t d8 ファイル … 8バイトずつ整数として（int64_t） od -A d -t f4 ファイル … 4バイトずつ小数として（float） od -A d -t f8 ファイル … 8バイトずつ小数として（double） od -A d -j 16 -N 8 -t f8 ファイル … 16バイト目から8バイトだけ、double として

問2-1 で確かめること・書くこと

  • practice.dat の大きさ 72 バイトを、1件の大きさで割ると何件か。
  • 上の表示で、1件目の番号・名前・気温がどこにあるかを指で追い、od -A d -t f8 -j 16 -N 8 practice.dat で 気温が 12.5 と出ることを確かめる。
  • 不思議なところ：番号（4バイト）＋名前（8バイト）＝12バイトなのに、気温は 16バイト目から始まっています。12〜15バイト目の4バイトは何でしょう？ practice_reader.c をコンパイルして動かし、表示される sizeof(struct record) の値と合わせて考えてください。
gcc -Wall -o practice_reader practice_reader.c
./practice_reader
こう表示されればOK
1件の大きさ sizeof(struct record) = 24 バイト
1  kyoto     12.50
2  nara      9.75
3  osaka     15.00
答え合わせ（問2-1の不思議なところ。自分で考えてから開く）
12〜15バイト目はパディング（詰め物）です。double は8バイトの数なので、Cのコンパイラは8の倍数の位置から始まるように置きます。12は8の倍数ではないので、4バイト空けて16から置きました。だから sizeof は 4+8+8=20 ではなく 24 です。
ファイルの中にもこの4バイトがそのまま入っているのは、構造体を write でそのまま書き出したからです。あなたのファイルにも、パディングがあるかもしれません。

printf '%s' 'syspro-mystery:1116249999' | sha256sum | cut -c1-10

printf '%s' 文字列文字列をそのまま出力する（echo と違って最後に改行を付けない。改行が付くと結果が変わってしまう）。

sha256sum受け取ったデータから、64文字の「指紋」（ハッシュ値）を計算する。1文字でも違えば、まったく違う指紋になります。

cut -c1-10各行の1文字目から10文字目までを取り出す。

表示された10文字が ○○○○○○○○○○ です。次のURLからダウンロードし、~/syspro/midterm に置いてください。

必須問2-3　1件は何バイトか、項目はどこにあるかを突き止める

ここからは記録を取りながら進めます。打ったコマンドがそのまま「根拠」になります。

cd ~/syspro/midterm
script kadai2.log                      # 記録を始める
ls -l mystery_*.dat                    # ファイルの大きさ（バイト数）を見る
od -A d -c mystery_*.dat | head -20    # まず文字として見て、場所の名前を探す
# ↓ ここから先は、自分で考えて od を打つ（下の「進め方」を参考に）
exit                                   # 記録を終える（続きは script -a kadai2.log で追記できる）
進め方この順番で考えると迷いにくい
  1. 名前を探す：od -A d -c で、k y o t o のような英字が見えるところを探す。名前が何バイトおきに現れるかを数える。それが1件の大きさの候補。
  2. 割り算で確かめる：ファイルの大きさが、その候補で割り切れるか。割り切れたら、件数も分かる。
  3. 時刻を探す：2026年10月ごろの時刻は、秒で数えると 1790000000 前後の数です。od -A d -t d4 や -t d8 で、その大きさの数が出る位置を探す。見つけたら date -d @その数 で日時に直して確かめる。
  4. 番号を探す：1件ごとに 1ずつ増える数を探す。-t d4 でも -t d2 でも見てみる。
  5. 気温を探す：5〜33くらいの小数になる位置を、-t f4 と -t f8 の両方で探す。でたらめな値（1.2e-300 のような値）が出たら、その読み方は違う。
  6. 残りを確かめる：どの項目にも入らないバイトが残ったら、それはたぶんパディング。全部 00 になっているはず。
date -d @秒数時刻に直す

何をする「1970年1月1日から何秒」という数を、ふつうの日時に直して表示します。TZ=Asia/Tokyo date -d @1790780400 とすると日本時間で表示されます（2026年10月1日 0:00 になるはず）。

od -w数1行の幅を変える

何をするod は普通1行に16バイト表示します。1件の大きさが分かったら、od -A d -t x1 -w24 ファイル のように1行をその大きさにすると、1行＝1件になって縦に同じ項目が並び、とても見やすくなります。

ヒント：数字がバラバラで、整数なのか小数なのか分からない
同じ4バイトでも、「整数として読む」か「小数として読む」かで、まったく違う数に見えます。バイトそのものには「型」は書いてありません（これがこの課題の核心です）。
だから、「意味の通る数になる読み方」を探します。時刻なら1790000000前後、気温なら5〜33くらい、番号なら1ずつ増える。全部の件で意味が通れば、その読み方で正しいと考えてよいでしょう。

用語集・困ったとき

用語集

システムコールプログラムがカーネルに仕事を頼むための窓口。open・read・write・close など。
バッファデータを一時的にためておく入れ物（メモリの一部）。bufcp では「1回に読む量」を入れる箱。
標準入出力ライブラリprintf・getc・fopen などの関数の集まり。中で自分のバッファを持ち、read/write の回数を減らしている。
ページ／ブロックメモリやディスクを管理するときの「ひとまとまり」の大きさ。多くの Linux では 4096 バイト。
レコード同じ形のデータ1件分。課題2では「番号・名前・時刻・気温」の4つで1件。
オフセットファイルや構造体の先頭から数えて「何バイト目か」。0から数える。
パディング構造体の項目と項目の間（や最後）に、コンパイラが入れる詰め物。数を決まった位置（4の倍数・8の倍数など）から始めるため。
UNIX時刻1970年1月1日0時（世界標準時）から数えた秒数。date +%s で今のUNIX時刻が見られる。
16進数0〜9とa〜fの16種類で数を表す書き方。1バイト（0〜255）がちょうど2桁（00〜ff）で書ける。
