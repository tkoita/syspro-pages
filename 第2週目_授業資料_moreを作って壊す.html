あなたのプログラムは、実は独りではない

1-1 単純なモデルと、実際に起きていること

あなたがこれまで書いてきたプログラムは、だいたい図1の①のような姿をしていたはずです。キーボードから入力が来て、処理して、画面に出す。ディスクを読んだり、プリンタに送ったりもする。プログラムが、装置に直接つながっているという絵です。

この絵にぴったり合うコードは、たとえば次のようなものです。標準入力を読んで、標準出力に書くだけ。

/* 標準入力を標準出力にコピーする */
int main(void)
{
    int c;
    while ((c = getchar()) != EOF)
        putchar(c);
    return 0;
}

ところが、実際のあなたのマシンは、この絵の通りにはなっていません。同じマシンには他の人がログインしているかもしれず、いまこの瞬間も何十というプログラムが同時に動いています。ディスクは1つしかないのに、複数のプログラムが同時に読み書きしています。キーボードは1つなのに、それを欲しがるプログラムは複数あります。

それでも①のつもりで書いたコードは、正しく動きます。なぜでしょうか。

図1：①は「単純なプログラムモデル」（教科書1.2.1）。②が実際の姿（同1.2.3〜1.2.4）。

答えは②の絵にあります。プログラムは装置に直結していません。あいだにカーネルという1つのプログラムが座っていて、すべての出入りを引き受けているのです。カーネルが交通整理をしてくれているから、あなたは①のつもりで書ける。

①が間違っているわけではありません。①のつもりで書いても動くように、カーネルが引き受けてくれているだけです。そして、その「引き受け」が通用しなくなる瞬間があります。——それは、プログラムが複数の口を同時に使おうとしたときです。

この一文を覚えておいてください。今日の演習で、まさにそれが起きます。「複数の口を同時に使おうとして、破綻する」。90分後、この文の意味が分かるようになります。

1-2 カーネルが管理している6つのリソース

カーネルが管理しているものは、教科書1.3.1で6つに整理されています。暗記する必要はありません。「システムプログラミングの守備範囲はこの6つ」という地図として見てください。

リソースカーネルがやっていることこの授業で扱う回
プロセッサどのプログラムに、いつCPUを渡すかを決めるプロセス管理の回
メモリプログラムとデータの置き場所を配る・守るプロセス管理の回

ここで大事なのは、プログラムがこれらに触りたいときは、カーネルに「依頼」しなければならないということです。勝手には触れません。この依頼のことをシステムコールと呼びます（詳しくは第4回以降）。

今日触るのは、この6行のうち「デバイス」の1行だけです。もっと正確に言えば、「端末（ターミナル）というデバイスに、どうやって話しかけるか」という1点だけ。90分で1行分。それでいいと思ってください。6行ぶん進むのに、この科目は1年かけます。

1-3 なぜ今、システムプログラミングなのか

正直に言えば、この科目はいちばん「古い」ように見えます。1970年代に設計された仕組みを、2026年に学ぶ。しかも、コードは生成AIが書いてくれる時代に。ここに、はっきり答えを出しておきます。

論点1AIが動いている場所は、例外なくLinuxである

大規模モデルの学習も推論も、実行環境はLinuxです。そして——ここが面白いところですが——「コンテナ」という実体は、どこにも存在しません。あるのは、名前空間（namespace）と資源制限（cgroups）というカーネルの機能を使って、「他が見えないように制限されただけのプロセス」です。

つまりコンテナが分かるとは、プロセスが分かるということです。逆に言えば、プロセスを知らないままコンテナを使うと、動いているうちは何とかなり、壊れた瞬間に何も分からなくなります。

論点2あなたは、AIが書いたコードを検収する側になる

今日の演習で見るバグは、文法的には完全に正しいコードが、システムの前提を勘違いしているために壊れるという型のバグです。コンパイラは何も言いません。警告すら出ません。それでも壊れます。

このタイプは、コードだけを眺めても絶対に見つかりません。「標準入力とは何か」「パイプでつないだとき何が起きるか」というOS側の知識がないと、バグが目の前にあっても、バグだと認識できない。

生成AIはコードを速く出します。速く出るからこそ、正しいかどうかを判定するコストが相対的に跳ね上がっています。判定できる人の価値が上がる、というのが今の状況です。

論点3AIエージェントは、あなたが今日打つコマンドを打っている

自然言語で指示すると、コードを書き、シェルコマンドを実行し、ファイルを読み書きし、プロセスを起動する——そういう道具が普通になりました。

そのログには、あなたが今日打つのと同じコマンド、同じパイプ、同じリダイレクトが並びます。読めなければ、承認も却下もできません。「読める人」であることの価値は、むしろ上がっています。

教科書の6リソースは、そのまま現代のAIインフラの用語に対応づけられます。概念の対応であって実装が同じという意味ではありませんが、地図としては十分に使えます。

教科書（1970s〜）いまの現場での「顔」
プロセッサアクセラレータの割り当て、cgroups によるCPU/メモリ制限、ジョブスケジューラ
メモリモデル重みの常駐と読み込み、ページキャッシュ、メモリ帯域がボトルネックになる話
デバイス/dev/ 以下のデバイスファイル経由でアクセスする、という構図は今もそのまま
プロセス管理コンテナ ＝ namespace ＋ cgroups。オーケストレータはその上の層
通信（IPC）推論サーバとワーカ間の受け渡し、共有メモリ、ソケット、パイプ
ネットワーク分散学習のノード間通信。計算より通信が効く局面が普通にある
まとめると、この科目の立場はこうです。
AIに奪われるのは「書く」作業であって、「どこが壊れているか判断する」作業ではありません。そして判断は、下の層を知らないとできません。

——今日壊れるコードは、その実演です。90分後に、この主張が正しかったかどうか、自分で判定してください。

1-4 この授業でのCopilotの使い方

ここは演習のルールです。禁止事項というより、今日の学習が成立するための条件だと思ってください。

◯ 使ってよい

  • コマンドやオプションの意味を聞く（ただし man で裏取りする）
  • コンパイルエラーの読み方を聞く

× 今日はやらない

  • 「more コマンドを作って」と丸投げする
  • 出力を貼って、動いたから終わりにする
  • Stage B で「なぜ止まらないのか」を、自分の仮説を書く前に聞く
★丸投げが禁止な理由は、ズルだからではありません。
Copilot は、正しい版の more を最初から出してくる可能性が高いです。つまり丸投げすると、「壊れる版」を一度も見ないまま、正解だけが手に入ります。

B-1 まず読む（5分）― コンパイルはまだしない

VSCode で more01.c を作り、下のコードを入れてください。入れたら、コンパイルする前に、その下の3問に答えてください。コードを読まずに実行すると、今日の学習が半分消えます。

/* more01.c ---- 自作 more バージョン 0.1 */
#include <stdio.h>
#include <stdlib.h>

#define PAGELEN 24        /* 1画面の行数 */
#define LINELEN 512       /* 1行の最大文字数 */

void do_more(FILE *fp);
int  ask_user(void);

int main(int ac, char *av[])
{
    FILE *fp;

    if (ac == 1) {                    /* 引数なし → 標準入力を読む */
        do_more(stdin);
    } else {
        while (--ac) {                /* 引数あり → ファイルを開いて読む */
            if ((fp = fopen(*++av, "r")) != NULL) {
                do_more(fp);
                fclose(fp);
            } else {
                perror(*av);
                return 1;
            }
        }
    }
    return 0;
}

void do_more(FILE *fp)
{
    char line[LINELEN];
    int  num_of_lines = 0;
    int  reply;

    while (fgets(line, LINELEN, fp) != NULL) {
        if (num_of_lines == PAGELEN) {      /* 1画面ぶん出した */
            reply = ask_user();
            if (reply == 0) break;            /* q → 終了 */
            num_of_lines -= reply;          /* 進む行数だけカウンタを戻す */
        }
        if (fputs(line, stdout) == EOF)
            exit(1);
        num_of_lines++;
    }
}

int ask_user(void)
{
    int c;

    printf("\033[7m--More--\033[m");   /* 反転表示でプロンプト */
    fflush(stdout);
    c = getchar();                     /* ← 今日の主役。どこから読んでいる？ */
    if (c == 'q') return 0;            /* 終了 */
    if (c == ' ') return PAGELEN;      /* スペース → 次の1画面 */
    return 1;                          /* それ以外 → 1行だけ */
}
コンパイル前に答える3問（隣の人と口頭で、1分ずつ）
① ac == 1 のとき、データはどこから来ますか？
② ask_user() の中の getchar() は、どこから1文字読みますか？
③ fflush(stdout) が無いと何が困りますか？（難問。分からなくてよい）
3問の答え（自分の答えを言ってから開く）

① 標準入力から。do_more(stdin) と書いてあります。stdin は「標準入力」を表す FILE * です。

② 標準入力から。getchar() は fgetc(stdin) と同じ意味です。——これが今日の全部です。いまは「ふーん」で構いません。

③ printf の出力は、すぐ画面に出るとは限りません。効率のため、いったんバッファにためられます。改行が無いと、たまったまま出ないことがあります。すると --More-- が表示されないまま、入力待ちで固まっているように見えます。fflush(stdout) は「たまっているぶんを、いま出せ」という指示です。

なぜ壊れたのか（仮説を書いてから開く）

原因は1つです。Q1 も Q2 も、同じことから起きています。

cat numbers.txt | ./more01 と書いた瞬間、more01 の標準入力は「パイプ」になります。つまり標準入力の中身は、表示すべきデータそのものです。

more01 は、データの通り道と、あなたの指の通り道が、同じ1本になっている。
